# 按改动范围验证

日常修改不再默认跑完整回归、打包和安装器。仓库使用同一个选择器生成本地与 Windows CI 的验证计划。

## 本地使用

尚未提交的修改（包括暂存、未暂存和未忽略的新文件）：

```powershell
python -m scripts.validate_changes --base HEAD --run
```

验证最近一个提交可用 `--base HEAD^`；连续修改应指定最后一次验证通过的提交。只查看计划时省略 `--run`。`build/validation-plan.json` 会列出改动文件、测试清单和选择原因。

- 仅对有改动的 Python 文件执行 Ruff 和格式检查。
- 普通模块沿 Python 的直接和间接导入关系选择测试，包括相对导入、函数内部导入和可解析的动态导入。
- 样式、插件目录、翻译资源和 Windows 集成采用明确的功能映射，避免主窗口的集中导入导致所有 GUI 测试都被选中。
- 改动测试文件时运行该文件及导入它的测试；重命名按新旧两条路径处理。
- 文档修改不启动 GUI 测试。无法判断影响范围时明确回退完整测试，不把未知文件当作无影响。
- 依赖、pytest 公共配置、公共测试夹具改动会扩大测试范围。新增动态消费者时应更新选择器映射与对应测试。

静态依赖和功能映射不能证明所有运行时调用，计划采用保守选择；不要为了缩短时间删除真实关联。相同范围通过后，不再额外重复窗口专项或完整回归。

## CI 与构建

PR 和普通 main 提交优先使用同分支最近一次成功验证、且仍是当前提交祖先的提交作为基线。除了任务成功，还会核对验证步骤确实完成；明确跳过测试的便携预览不作为验证基线。查不到验证历史时使用 PR 基准或 push 前提交；历史不可用时完整验证。这样后续提交不会重复测试整个 PR 中已经验证过的代码，基准分支合入带来的变化也会纳入差异。手动仅请求重新打包、且当前提交已经验证通过时，可复用当前成功提交，只验证新构建的产物。

普通 UI 和业务修改只运行相关测试，不自动打包。打包脚本、原生处理器或安装集成变化会触发对应的构建与验证。主窗口专项已包含在测试清单中，不再重复运行；原生 DLL 和安装器也不再先编译一次相同的预检产物再重复构建。

需要产物时，可在手动工作流中选择 `portable` 或 `all`，或者在提交中使用 `[build]`（便携版）或 `[installer]`（便携版与安装版）。生成完整程序产物仍需通过实际打包程序和目录迁移验证；涉及安装版时还要通过安装、升级、可选集成和卸载验证。`--artifacts` 参数在本地生成相应计划，实际 Windows 构建仍使用分发文档中的命令。

明确请求的 `[portable-preview]` 仍只适用于 PR，产物标为未验证预览，不用于 Release。main 的 `[release]` 提交始终执行一次完整回归和完整分发验证，通过后才允许先上传草稿附件、再公开 Release。日常小改动无需用 `[skip ci]` 绕过验证。
